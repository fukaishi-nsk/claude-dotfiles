# nanco-status-update — 顧客の状況を Linear に書く

## 目的
nanco顧客の「今どうなっているか」を、Nスケッチのメンバーとメンバーの AI が一目で分かるようにしておく。
手で更新すると続かないので、顧客とのやりとりが動いたタイミングで AI が書く（2026-10-08 深石さん指示で導入）。

## 正本は Linear（2026-11-20〜）
- **正本: Linear のチーム `NANCO-CRM`（イシュー番号 CRM-◯◯）**。1社1イシュー
  - 2026-11-19 の朝会で、藤波さんの Linear CRM に寄せることになり、11/19 に Notion の動いている21社を移した。11/20 の朝会で「今後の Linear との同期・全体のステータス管理は深石さん」となり、同日に深石さんが「どちらかを正本にして同期」と決めた
- **Notion「🫂 Customers」DB は写し**。毎朝 Mac mini の定期タスク `nanco-crm-notion-sync` が Linear → Notion の一方通行で写す。**Notion の行を直接書き換えない**（翌朝 Linear の内容で上書きされる）
  - 例外: 面談ページを Customers の行に紐づけるために、行がまだ無ければ Notion に行を作るのはよい（nanco-consult-prep）。そのときも同じ内容を Linear に書く
- 藤波さんの対応表（Linear ドキュメント「notionとの対応表」 https://linear.app/nsketch/document/notionとの対応表-ce079902402d ）が列の対応の元

## 毎朝のボット（藤波さん作・触らない）
- 毎朝 9:18 ごろ、各ワークスペースの利用状況を本文の「## 自動の記録」に書き直し、ラベルとコメントを付ける。新しいワークスペースにはイシューを新しく作る
- ステータス・ボール・「## 最新の状況」・期日は変えない（11/20 の実行で、こちらが書いた節が残ることを確かめた）
- イシューとワークスペースは本文の `shortId` で結びついている（shortId を書いておけば重複して作られない。CRM-99 ノジマで確認）
- **「## 自動の記録」の節は書き換えない**

## イシュー本文の型
```
## 基本情報

* shortId: `XXXXXX`            ← ボットが書く。ワークスペースが無ければ「ワークスペース: 未作成」
* アプリ: …                     ← ボットが書く
* Customers: [社名](<Notion の行の URL>)   ← 写しの対応づけに使う。必ず入れる
* 経路: レディクル              ← レディクル案件のときだけ
* どんな会社: …
* 窓口: …

## nanco利用状況

* 利用状況: 利用中／ベータ版／営業中／導入候補／導入待ち／営業済み／離脱／パートナー商談中
* 契約: …（分かるときだけ）
* トライアル期限: YYYY-MM-DD（管理画面の Next Date。分かるときだけ）

## 自動の記録        ← ボット専用

## 最新の状況

* ボール: こちら（深石）／こちら（姉崎）／先方／打合せ予定／様子見
* 最終接触: YYYY-MM-DD
* 確認日: YYYY-MM-DD
* 現状: …
* 次のアクション: …
* 根拠: …
```
- 1つの会社に複数のワークスペースがあるとき（茂原と各拠点など）は、主のイシューに全部書き、ほかのイシューの基本情報には「会社の情報と最新の状況は CRM-◯◯ に書く」と1行だけ置く
- 題名は会社名にする（ボットはワークスペース名で作るので、「マイワークスペース」などは会社名に直す。直すときは基本情報に「ワークスペース名は「…」」と残す）

## 各欄の書き方
| 欄 | 書き方 |
|---|---|
| どんな会社 | 思い出すための1行（〜70字）。所在地・業種／何をどれくらい管理しているか（数字）／nancoで解決したいこと。顧客マスタ・KB・メモリ・メールにある事実だけ。不明は「未確認」 |
| 窓口 | 先方の主な担当者1〜2名（名前＋部署・役職）。分からない部分は「未確認」 |
| ボール | 下の「ボールの基準」で決める |
| 現状 | 今どうなっているかを1行で。最新の事実だけで、経緯は書かない |
| 次のアクション | 誰が何をするか。「できたら連絡します」の約束や社内の NANCO タスクはここに書く |
| 期日 | **イシューの期日（dueDate）**に入れる。次のアクションの期日。一次情報に期日があるときだけ（打合せ予定なら打合せの日） |
| 最終接触 | 顧客との最後のやりとり（メール・会議・LINE。向きは問わない） |
| 経路 | レディクル経由なら「経路: レディクル」（会議名が `[レディクル]…`、または rc_support@frontier-gr.jp から受付番号つきのメールが来ている）。それ以外は書かない |
| 利用状況 | 上の選択肢から選ぶ（Notion の選択肢と同じ言葉にする。写しで使うため） |
| 確認日 | 一次情報で確かめた日（今日） |
| 根拠 | メール件名＋日付・NANCO 番号＋状態・Slackの日時など。他の AI が追跡できる粒度で |

- 推測は「推定」、確かめていないことは「未確認」と書く。空欄を推測で埋めない

## ボールの基準（2026-10-08 深石さん確定）
会話の上で、次に動くのは誰か。

- **こちら（深石）／こちら（姉崎）**: 先方が、こちらの返信や成果物を待っている（未返信の質問・依頼、約束した資料が未送付、受け取ったデータの結果を未回答など）
- **先方**: こちらが最後に送り、先方の返事や行動を待っている
- **打合せ予定**: 次の打合せの日程が決まっている
- **様子見**: どちらも動く予定がない
- （離脱したら、ボール行を消さずに「様子見」にし、ステータスを Canceled・利用状況を離脱にする）

判定のしかた:
1. 最後のメッセージの向きを、スレッドを開いて確かめる（一覧行やスニペットで決めない）
2. こちらが最後に送っていても、その中で「◯◯を送ります」と約束した成果物が未送付なら「こちら」
3. 「反映したら連絡します」のように、先方が止まっていない約束は「先方」のまま、次のアクションに書く
4. 社内の NANCO タスクが残っているだけでは「こちら」にしない（2026-10-08 にこれを混ぜて16社を「こちら」にし、深石さんに「認識が違う」と指摘された）
5. 担当の分け方: メール・請求・フォローは深石さん、開発・資料作成・デモ・LINE で姉崎さん宛ての依頼は姉崎さん

## ステータスの決め方（藤波さんの対応表）
ステータスは「こちらが手を付けているか」だけを表す。ボールとは別。
| ボール | ステータス |
|---|---|
| 様子見 | Backlog |
| こちら（深石／姉崎） | 手を動かし始めたら In Progress。決めただけで未着手なら Todo |
| 先方 | こちらが渡して反応待ちなら In Review。何も出していないなら Backlog |
| 打合せ予定 | Todo か In Progress（日程は期日） |
- 利用状況が離脱なら Canceled。有料で個別対応が要らなくなったら Done
- 迷ったら今のステータスを変えず、報告に「要確認」と書く

## 手順
1. **対象のイシューを探す**: `list_issues`（team `NANCO-CRM`, query=社名の一部）。見つからなければ、ワークスペースの shortId（管理画面で調べる）、窓口の名前、顧客フォルダ名で引き直す。ボットが作ったイシューは題名がワークスペース名なので、shortId で引くのが確実
2. **一次情報を確かめる**: 呼び出し元の作業（会議の文字起こし、送信済みメール、LINE 転写、NANCO のイシュー）を根拠にする。トライアル期限を書くときは管理画面（`/admin/workspaces?search=<社名>`）を読む
3. **書く**: `save_issue` の `patch` で「## 最新の状況」の節だけを置き換える（本文全体を送り直さない。ボットの「## 自動の記録」を消さないため）。最新の状況が無いイシューには、`## nanco利用状況` の節の後ろか本文の末尾に足す。期日は `dueDate`、ステータスは上の表で `state`
4. **コメントを1行足す**: `save_comment` で「11/20 メール送信『件名』→ボール 先方」のように、何が動いたかを1行。藤波さんの決めたやり方（11/19 朝会「メールやミーティングのときにコメントを残す」）
5. **書けたか確かめる**: `get_issue` で読み直し、最新の状況と自動の記録の両方が残っていることを確かめる
6. **報告する**: 「◯◯社（CRM-◯◯）: ボール 先方→こちら（姉崎）、現状…」のように、変えた欄だけを1〜2行で呼び出し元の報告に含める

### イシューが無いとき（新規顧客）
- 顧客フォルダが既にある（＝新規顧客として承認済み）、またはオンライン相談の予約がある相手なら、`NANCO-CRM` にイシューを作ってよい。題名＝会社名（無ければ氏名＋「さん」）。上の型で、どんな会社・窓口・利用状況（営業中かベータ版）・最新の状況を埋める。ワークスペースがあれば shortId と アプリ の行も書く（ボットとの重複を防ぐ）
- Notion の Customers に行があれば、その URL を「Customers:」に入れる。無ければ空けておく（翌朝の写しで行が作られ、リンクも入る）
- フォルダも無い・社名が曖昧なときは作らず、報告で確認する
- 後からボットが同じ会社のイシューを別に作ったら（shortId が無かった場合に起きる）、勝手に消さず、報告に「CRM-◯◯ と CRM-◯◯ が同じ会社。統合要」と書く

## 書き込みの承認
- `NANCO-CRM` のイシューの最新の状況・期日・ステータス・コメントの更新と、新規顧客のイシュー作成は、2026-10-08 の仕組み化の指示と 2026-11-20 の「Linear を正本にして進めて」で**事前承認済み**。都度の確認は要らない。変えた内容は必ず報告する
- イシューの削除・統合、ラベルやステータスの種類の変更、ボットの節の編集、ほかの人のコメントの編集は承認を取る
- 無人実行でも更新してよいが、判定に迷うもの（ボールが決めきれない・顧客を特定できない）は触らず、Slack の報告に「要確認」として載せる

## 週次の棚卸し（nanco定例の前）
1. `NANCO-CRM` のイシューのうち、最新の状況があるもの（ボールが様子見以外）を引く
2. 確認日が7日より古いものを、一次情報（Gmail スレッド・NANCO のイシュー・Slack `#nanco_line` C0C5Z16821X・管理画面の Trial 一覧）で確かめ直す
3. 「こちら」のものと、期日を過ぎたものを、定例用に一覧で報告する
4. 量が多いときはエージェントを顧客グループごとに並列に走らせる（読み取りだけをさせ、書き込みは呼び出し元でやる）

## Linear が使えない環境
Codex など Linear MCP が無い環境では更新しない。更新すべき内容（社名・欄・値・根拠）を報告に書き、Claude Code で反映してもらう。
