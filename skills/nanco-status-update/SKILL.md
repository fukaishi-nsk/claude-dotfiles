# nanco-status-update — 顧客ステータス一覧の更新

## 目的
nanco顧客の「今どうなっているか」を、Nスケッチのメンバーとメンバーの AI が一目で分かるようにしておく。正本は Notion「🫂 Customers」DB。
手で更新すると続かないので、顧客とのやりとりが動いたタイミングで AI が該当行を更新する（2026-10-08 深石さん指示で導入）。

## 定数
- DB: https://app.notion.com/p/2ecb60a44ee84e88adc236122ccb9771 （Sales Wiki 配下）
- data source: `collection://842d7d57-058d-4df8-a229-9cea0a2eadaf`
- ビュー: 「ボール別」（ボード）／「動いている顧客」（表）。どちらもボールが空欄の行は出さず、「経路」の絞り込みが付いている。「レディクル案件」（表）は経路＝レディクルの行だけを出す
- タイトル列は `Proposal`（会社名）

## 列と書き方
| 列 | 型 | 書き方 |
|---|---|---|
| どんな会社 | text | 思い出すための1行（〜70字）。所在地・業種／何をどれくらい管理しているか（数字）／nancoで解決したいこと。顧客マスタ・KB・メモリ・メールにある事実だけ。不明は「未確認」。会議で新しく分かったら書き足す |
| 窓口 | text | 先方の主な担当者1〜2名（名前＋部署・役職）。分からない部分は「未確認」 |
| ボール | select | 下の「ボールの基準」で決める |
| 現状 | text | 今どうなっているかを1行で。最新の事実だけで、経緯は書かない |
| 次のアクション | text | 誰が何をするか。「できたら連絡します」の約束や社内のLinearタスクはここに書く |
| 期日 | date | 次のアクションの期日。一次情報に期日があるときだけ（打合せ予定なら打合せの日） |
| トライアル期限 | date | 管理画面の Next Date。推測で入れない |
| 最終接触 | date | 顧客との最後のやりとり（メール・会議・LINE。向きは問わない） |
| 経路 | select | レディクル経由なら「レディクル」（会議名が `[レディクル]…`、または rc_support@frontier-gr.jp から受付番号つきのメールが来ている）。それ以外は空欄のまま（推測で埋めない） |
| 利用状況 | select | 既存の選択肢を使う（利用中／ベータ版=トライアル／営業中／導入候補／導入待ち／営業済み／離脱／パートナー商談中） |
| 確認日 | date | この行を一次情報で確かめた日（今日） |
| 根拠 | text | メール件名＋日付・Linear番号＋状態・Slackの日時など。他の AI が追跡できる粒度で |

- `memo` 列は人が書く欄なので触らない
- 推測は「推定」、確かめていないことは「未確認」と書く。空欄を推測で埋めない

## ボールの基準（2026-10-08 深石さん確定）
会話の上で、次に動くのは誰か。

- **こちら（深石）／こちら（姉崎）**: 先方が、こちらの返信や成果物を待っている（未返信の質問・依頼、約束した資料が未送付、受け取ったデータの結果を未回答など）
- **先方**: こちらが最後に送り、先方の返事や行動を待っている
- **打合せ予定**: 次の打合せの日程が決まっている
- **様子見**: どちらも動く予定がない
- **空欄**: 離脱した、または7月以降に動きがない（ビューから消える）

判定のしかた:
1. 最後のメッセージの向きを、スレッドを開いて確かめる（一覧行やスニペットで決めない）
2. こちらが最後に送っていても、その中で「◯◯を送ります」と約束した成果物が未送付なら「こちら」
3. 「反映したら連絡します」のように、先方が止まっていない約束は「先方」のまま、次のアクションに書く
4. 社内の Linear タスクが残っているだけでは「こちら」にしない（2026-10-08 にこれを混ぜて16社を「こちら」にし、深石さんに「認識が違う」と指摘された）
5. 担当の分け方: メール・請求・フォローは深石さん、開発・資料作成・デモ・LINE で姉崎さん宛ての依頼は姉崎さん

## 手順
1. **対象の行を探す**: SQL で `"Proposal" LIKE '%<社名の一部>%'` を引く。表記ゆれ（株式会社の有無・略称）に注意。見つからなければ顧客フォルダ名でも引き直す
2. **一次情報を確かめる**: 呼び出し元の作業（会議の文字起こし、送信済みメール、LINE 転写、Linear）を根拠にする。トライアル期限を書くときは管理画面（`/admin/workspaces?search=<社名>`）を読む
3. **更新する**: `notion-update-page` の `update_properties`。日付は `date:<列>:start` と `date:<列>:is_datetime=0`。必ず確認日（今日）と根拠も更新する
4. **書けたか確かめる**: 同じ行を SQL で読み直し、値が入ったことを確かめる
5. **報告する**: 「◯◯社: ボール 先方→こちら（姉崎）、現状…」のように、変えた列だけを1〜2行で呼び出し元の報告に含める

### 行が無いとき（新規顧客）
- 顧客フォルダが既にある（＝新規顧客として承認済み）なら、新しい行を作ってよい。利用状況は営業中かベータ版。レディクル案件なら経路も入れる。どんな会社・窓口も必ず埋める（初回相談の文字起こし・レディクル報告書・予約メールから）
- フォルダも無い・社名が曖昧なときは作らず、報告で確認する

### Notion の「Query Data Source」が上限に達したとき（2026-10-08 実発生）
- SQL・rows・view モードの読み出しは、ワークスペースのプラン上限があり、1日に何十回も叩くと `usage_limit_reached` で止まる（書き込み＝update_page は止まらない）
- 行を探す: `notion-search` に `data_source_url=collection://842d7d57-…` と社名を渡す。書いた後の確認: `notion-fetch` でそのページを開き properties を読む
- 一覧の集計（週次の棚卸しなど）は上限が戻ってからやる。止まったことは報告に1回書く

## 書き込みの承認
- この DB の行の更新・追加は、2026-10-08 に深石さんが仕組み化を指示したため**事前承認済み**。都度の確認は要らない。変えた内容は必ず報告する
- 列の追加・削除、選択肢の変更、行の削除、他の人が書いた memo の編集は承認を取る
- 無人実行（クラウド routine など）でも更新してよいが、判定に迷う行（ボールがどちらか決めきれない・顧客を特定できない）は触らず、Slack の報告に「要確認」として載せる

## 週次の棚卸し（nanco定例の前）
1. ボールが空欄でない行を全部引く
2. 確認日が7日より古い行を、一次情報（Gmail スレッド・Linear・Slack `#nanco_line` C0C5Z16821X・管理画面の Trial 一覧）で確かめ直す
3. 「こちら」の行と、期日を過ぎた行を、定例用に一覧で報告する
4. 量が多いときはエージェントを顧客グループごとに並列に走らせる（読み取りだけをさせ、書き込みは呼び出し元でやる）

## Notion が使えない環境
Codex など Notion MCP が無い環境では更新しない。更新すべき内容（社名・列・値・根拠）を報告に書き、Claude Code で反映してもらう。
